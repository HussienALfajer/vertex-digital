# apps/store

The customer site at `digital.vertexmedia.pro`: Next.js 16 (App Router, Turbopack, Cache Components), Arabic RTL, dark by default (ADR 0002, 0011, 0012). Read `brand/identity.md` (§6 is the store's own guidance) before visual work.

## Rules
- Server components by default; `'use client'` only for interaction. A page must stay static or cached: never read cookies or the session in a server component of a public page; customer-specific parts load in the browser (as `AccountLink` does) until a feature's spec says otherwise.
- With Cache Components, anything time- or request-dependent sits inside `'use cache'` (tagged per entity once the catalog exists, ADR 0002) or a `<Suspense>` boundary; the build fails otherwise.
- Cached reads of the API (pattern: `src/features/catalog/data.ts`): a `'use cache'` function with `cacheTag` from `lib/cache-tags` and `cacheLife`, called from a server component inside `<Suspense>` after `await connection()`, so it runs at request time and never during the build (the API may be away then); the result is then served from the cache until the worker expires its tag. A failed read throws (never cached) and the route's error view offers a retry. Only public routes, no cookie: what a customer owns loads in the browser.
- Money formatting and the contracts' schemas (zod) stay out of a page's first load: render prices in server components and pass them to client components as `children` (`PackContent` into `PackButton`), and load heavy client parts with `next/dynamic` when they are first needed (the buy box, the calculator's body, the search dialog).
- Anything a field's blur changes must not move what sits under the pointer: the player check's status has a fixed slot, or the press on "متابعة" that blurred the field loses its click.
- UI from `@vertex-digital/ui` through its subpaths only (`@vertex-digital/ui/components/button`, `@vertex-digital/ui/brand/logo`), never the root barrel: the barrel puts every client component in the first load. Missing component: add it to `packages/ui`.
- Logical CSS only; `packages/ui/src/conventions.test.ts` checks this folder too. Touch targets at least 44 px (`size="xl"` buttons, `h-11` inputs); inputs use `text-md` so phones do not zoom.
- Text only through `t('<area>.<key>')`, Arabic copy per `brand/identity.md` §10 (no exclamation marks, every error says what to do next). Server errors show `errors.<code>` through `errorText()`, never the server's message. Fields for LTR values (email, password, IDs) set `dir="ltr"`.
- Account pages are static shells; everything about the customer loads in the browser with the session cookie and is never cached. No personal data in URLs: the address waiting for its code travels in session storage (`features/auth/pending-email.ts`).
- Image previews of local files use data URLs: the CSP allows `img-src 'self' data:`, not `blob:`.
- Read query parameters with `useSearchParam` (after hydration), not `useSearchParams`, so pages stay static without a Suspense boundary. Exception: inside a boundary a dynamic route already needs (the game page's `?pack=`, which a search result can change without a reload; `/orders?checkout=` inside its own boundary, S10), `useSearchParams` follows the URL.
- The store's CSP allows inline scripts so pages stay cached (ADR 0015): `dangerouslySetInnerHTML` only for constant strings written in this repository (the theme script, S14's announcement dismissal script, the session hint script), never for data from the API or customers.
- API calls go to `/api/...` on the same origin (nginx in production, a rewrite to the API in development). Customer auth is Better Auth at `/api/auth`.
- Links on every page (header, footer, banners) to an account or support page set `prefetch={false}`: Next prefetches links in view, and those pages' code (forms, zod, ALTCHA) would count in every short page's first load (S12: the footer's "الدعم" took the game page from 228 to 324 KB).
- Brand files are imported from `brand/` (`layout.tsx` icons), never copied into a `public/` folder. The one exception is `src/app/favicon.ico`, which the App Router serves only from there.
- A refused submit takes the customer to the first refused field (2026-10-14): every form puts `ref` from `useFocusInvalid()` (`@vertex-digital/ui/focus-invalid`) on its `<form>` (or the element holding its fields, as the buy box) and calls `focusInvalid()` wherever it refuses, before sending and after a server refusal named a field; fields mark themselves through `Field invalid` and `aria-invalid` (a container a field has not, a fieldset of choices, sets `data-invalid`). `InvalidAlert` (`forms.invalid`) sits beside the submit button while fields are refused, except where the only field is right above the button. Pattern: `src/features/auth/sign-up-form.tsx`, `src/features/deposits/deposit-form.tsx`.
- Performance budget (`e2e/store.spec.ts`): first load of `/` at most 215 KB of JS (200 until S05, 205 until S09, 210 until S14: the whole Arabic catalog ships in it; measured 206 in S09 PR 3, 212 in S14 PR 2 with the content strings, the carousel and the announcement's close button) and 20 KB of CSS, gzipped; the four content pages and `/faq` at most 215 KB of JS (S14); the game page `/games/[slug]` at most 235 KB of JS and 20 KB of CSS (measured 223 and 9 in S09 PR 3, the buy box not chosen yet; 226 in S10 PR 2; raised from 230 on 2026-10-15, when the refused-form alert's catalog string took it to 231 in CI); `/cart` at most 385 KB of JS (measured 373 in S10 PR 2: the cart's rules and slide-to-pay load with it; raised from 380 on 2026-10-15, when the server clock in `apiRequest` (F3-2) took it to 381 in CI) and a share page `/g/<token>` at most 217 (measured 210: its card renders on the server; raised from 215 on 2026-10-19, when the header's signed-in placeholder took it to 216 in a full run). The home page measured 209 in S10 PR 2; S12 PR 2 measured 210 (home, at the budget: the support strings), 228 (game page), 375 (cart), 211 (share page). S20 PR 3 raised the home page, the content pages and `/faq` to 218, the game page to 238 (measured 236), the share page to 220 and `/cart` to 390: the merchant strings in the catalog every page ships (measured 217, 219 and 389). ## Tests
- Unit: `src/**/*.test.ts` (Vitest), next to the code.
- E2E (`e2e/`): against the production build on port 4001; server components read the catalog from `e2e/catalog-server.mjs` (port 4002, fixed answers from `e2e/catalog-fixtures.json`; `e2e/catalog.ts` builds the search index and finds packs from the same data), and a second store on 4003 reads an empty catalog (`EMPTY_STORE_URL`, `e2e/servers.ts`), and a third on 4004 reads published content (`CONTENT_STORE_URL`, S14: `e2e/content-fixtures.json`; the other two read none); in the browser the API is mocked per test with `api.on('METHOD /path', status, body)` (`api.last(key)` reads what was sent; an empty wallet (S22: with no reservations), no quick-buy cards (S22), no product alerts (S22; a key with its query string, `GET /api/product-alerts?status=ended`, wins over the bare path), an empty notification stream and every email choice on are answered by default, since the header reads the first two on every signed-in page; `api.stream(key, events, delayMs?)` answers server-sent events, after a delay when a test changes what the page reads next; catalog images answer a PNG by default), and a request without a mock fails the test, as do page and console errors. Service workers are blocked in every spec but `e2e/pwa.spec.ts` (`serviceWorkers: 'block'` in `playwright.config.ts`); push flows replace the browser's push side with `e2e/push-browser.ts`. Next.js keeps the previous page mounted but hidden after a client navigation: find fields among the visible ones (`accounts.spec.ts`, `field()`). `pwa.spec.ts` checks that `/favicon.ico` and every icon the head and the manifest link answer 200. Every new screen adds RTL screenshots, dark and light, at phone width and desktop (the `phone` and `desktop` projects).

Run: `pnpm --filter @vertex-digital/store test` · `pnpm --filter @vertex-digital/store typecheck` · `pnpm test:e2e` (builds first) · dev: `pnpm dev` (port 3001, with the API on 3000).
