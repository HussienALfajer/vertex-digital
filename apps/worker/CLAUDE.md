# apps/worker

NestJS standalone context for background work (ADR 0001, 0002): pg-boss queues and schedules; later fulfilment, supplier sync and polling, webhook processing, USDT verification, the Telegram admin bot and email. It never serves HTTP.

## Layout
- `src/main.ts` (imports `instrument.ts` first: Sentry), `src/worker.module.ts`.
- `src/core/`: `config` (Zod env), `database` (`DATABASE` token, app role), `jobs/pg-boss.service.ts`, `alerts/telegram-alerts.ts`, `alerts/scrub-breadcrumb.ts` (keeps the bot token out of Sentry), `email/mailer.ts` (Nodemailer over SMTP, or `.eml` files under `EMAIL_LOG_DIR` when `EMAIL_TRANSPORT=log`, the default outside production).
- `src/jobs/<area>/<name>.job.ts`: one queue per file. Pattern to copy: `src/jobs/system/heartbeat.job.ts` (scheduled), `src/jobs/email/send-email.job.ts` (a row locked and settled once, failures recorded and retried). `jobs/email/`: `email.send`, `email.purge-codes` and the Arabic templates (`email-templates.ts`). `jobs/deposits/expire.job.ts`: `deposits.expire` (batches locked with `FOR UPDATE SKIP LOCKED`, an audit entry each). `jobs/deposits/usdt-verify.job.ts` and `usdt-scan.job.ts` (S04): `deposits.usdt-verify` and `deposits.usdt-scan`, pattern to copy for a job that reads an outside service, settles under a row lock, and schedules its own next run; their shared writes in `usdt-settle.ts` (record, bind, credit through `creditUsdtDeposit`, bounce), the pure decision in `usdt-assess.ts`. `jobs/deposits/chain/`: the chain readers (`ChainReader`, `ChainReaderError`; `TronReader`, `BscReader`, `FakeReader` with a file or memory store; `CHAIN_READERS` from `chain-readers.provider.ts`), with synthetic fixtures. A customer event from a job: `notifyCustomer(tx, bossJobSender(boss), …)` from `@vertex-digital/db` (S05 rule NT1: the notification, its email unless turned off, the live event at commit). `src/cli/usdt-fake-transfer.ts`: the development CLI. `src/telegram/` (S05 F07, ADR 0019): `bot-api.ts` (`TelegramBot`, the only holder of the token: the Bot API, or JSON files under `TELEGRAM_LOG_DIR` when `TELEGRAM_TRANSPORT=log`; `TelegramApiError` with `retryAfter`), `messages.ts` (the Arabic text and buttons of each outbox kind), `linked-chat.ts` (the live link's chat for alerts, cached 60 s), `webhook-setup.ts` (`setWebhook` at start). `jobs/telegram/send.job.ts`: `telegram.send`; `deposit-card.job.ts`: `telegram.deposit-card` (a deposit's card: the receipt from the API's `FILES_ROOT`, re-encoded to JPEG with sharp, sent while it waits and edited to the outcome); `review-reminder.job.ts`: `telegram.review-reminder` (with `waitingDeposits`, shared by the summary); `daily-summary.job.ts`: `telegram.daily-summary` (22:30 Damascus). `messages.ts` also renders the deposit cards (`renderDepositCard`) and the supplier messages (S07). `src/suppliers/` (S07): `supplier-registry.ts` (`SupplierRegistry`: `get(code, credentials)` for the adapters this build has, `connect(db, supplier)` decrypting the newest credentials per call with `SUPPLIER_KEYS_SECRET`), `supplier-calls.ts` (`recordedCall`: every adapter call into `supplier_calls`, `refused` for a definitive refusal, `error` otherwise; `sanitizedMessage`: credentials masked, URL queries dropped), `fake-state-file.ts` (the fake supplier's scripted state). `jobs/suppliers/`: `sync.job.ts` (`suppliers.sync`, SY1–SY4: one running run per supplier, the call outside any transaction, then offers, cost changes, repricing and the run's end in one; `failedRunStreak` for the failing-sync alerts), `sync-schedule.job.ts`, `balances.job.ts` (H5), `health.job.ts` (H1–H4, the probe, SY5's stale repricing): pattern to copy for a job that calls a supplier and reprices. `src/cli/supplier-fake.ts`: the fake supplier's development CLI (S08: `--order` scripts an offer, `--resolve` settles an order's open fake attempt and, `--via webhook`, posts its signed webhook to the local API). `jobs/orders/` (S08): `fulfil.job.ts` (`orders.fulfil`, R1–R6: routing under the order lock with `orderCandidates`, the attempt committed before the call, the answer through `applyOutcome`; a manual attempt waits with its `manual_order` card), `poll.job.ts` (`orders.poll`, F3: `getOrder` for a pending attempt, `placeOrder` again with the key for a `sending` or `unknown` one), `sweep.job.ts` (`orders.sweep`, every minute, F6, F7, MN2: lost sends and polls queued again, the hard limit's hold with its alert and the customer's `order_delayed`, the manual reminder, lost routing runs), `order-calls.ts` (`askSupplier`: the call recorded with the order outcome's health result, the answer classified for the write path; `orderContext`). `jobs/suppliers/webhook.job.ts`: `suppliers.webhook` (F5). The fake's orders are kept in its state file (`keepFakeOrder`, one change at a time) so polls and `--resolve` find them. Logs redact `codes` (`core/config/log-redact.ts`).

## Rules
- Queue names are `<area>.<action>` (`system.heartbeat`), exported as constants next to the job; names shared with the API go in `packages/contracts`.
- Register a job in `onApplicationBootstrap` with `PgBossService.work(queue, handler)`, which creates the queue (with its policy from `QUEUE_POLICIES` in the contracts, as the API does) and reports a failure to the logs, Sentry and the alert channel before pg-boss retries it. Schedules: `boss.schedule(queue, cron)` after `work`.
- Every job is idempotent: pg-boss retries, so running it twice leaves the same result (upsert, check-then-act inside a transaction, idempotency keys on supplier calls).
- Payloads carry ids, not records: load fresh data inside the job.
- pg-boss runs as the app role (ADR 0014): `createPgBoss` from `@vertex-digital/db` never creates or migrates tables and never rebuilds indexes. Queues are unpartitioned (rows only). pg-boss's tables are installed by the owner with the migrations.
- Money moves only through `postJournal`, order states only through the order write path in `packages/db` (ADR 0003, 0004). Supplier calls go through `packages/suppliers`; a call with an unknown outcome is resolved by polling, then the admin, before any other route (ADR 0005).
- Alerts: `TelegramAlerts.send(text)` (rate limited, repeats suppressed for ten minutes, sent to the linked chat, logged and dropped with no link or without `TELEGRAM_BOT_TOKEN`). Other bot messages go through the outbox (`queueTelegramMessage` from `@vertex-digital/db`), never straight to Telegram. Never put tokens, keys, receipts or personal data in an alert; ids and error messages only. `TelegramAlerts.suppressedOn(date)` counts what the rate limit held back that Damascus day, for the summary.
- Files: the worker reads the API's stored files read-only (`FILES_ROOT`; a relative path resolves from `apps/api`, where the API runs). It never writes there.
- Logs through the Nest logger, never `console.log`.
- Suppliers are called only through `SupplierRegistry` and `recordedCall` (S07, ADR 0005): every call recorded, credentials decrypted per call and never logged, stored, put in jobs or alerts; a run's error message goes through `sanitizedMessage`. A supplier's failure is recorded (a failed run, a call), never thrown to pg-boss; only a fault of ours fails the job.
- Chains are read only through `CHAIN_READERS` (S04, ADR 0006): a `ChainReaderError` concludes nothing (rule U6), so a job catches it, schedules its next read and alerts; it never throws it to pg-boss as a failure. Readers are pure HTTP clients (no database, no Nest, no `process.env`), every reply parsed with Zod, 10-second timeouts, no retry inside.

## Tests
`test/` against the test database with a unique `WORKER_NAME` and `EMAIL_LOG_DIR` per run (emails are files, never sent); the Telegram channel and `telegram.send` against a local fake Bot API, the send, card, reminder and summary jobs inside a rolled-back transaction (the live link, the bot state and the settings are shared by every test file; fixed instants in 2030 keep the reminder and summary apart from other rows); bot messages are files in a directory of their own per run (`TELEGRAM_LOG_DIR`). Nothing calls Telegram, a supplier or a chain in tests: readers are tested with a scripted `fetch` and the fixtures (`test/chain-readers.test.ts`); the USDT jobs with the memory fake chain and pg-boss stubbed, so no background run races the test (`test/deposits-usdt.test.ts`). The order jobs (`test/orders.test.ts`) run with the in-process fake supplier, its orders kept in memory, each test in a rolled-back transaction that moves other tests' routes off the fake offers it uses; the two race tests commit new rows on their own offers. The supplier jobs (`test/suppliers.test.ts`) run with scripted adapters, each test in a rolled-back transaction that first moves the other tests' fake offers and routes out of the way; the `fake` supplier's rows are shared with the api and db tests, so turbo runs the worker's tests after theirs (`turbo.json`). Vitest emits decorator metadata through oxc (`vitest.config.ts`).

Run: `pnpm --filter @vertex-digital/worker test` · `pnpm --filter @vertex-digital/worker typecheck`.
