# packages/db

Drizzle schema, migrations, the database client and the shared money write paths (ADR 0002, 0003, 0011, 0014). Schema changes follow the `db-migration` skill.

## Layout
- `src/schema/<module>.ts`: tables of one owning API module (`wallet.ts`: the ledger, the wallet adjustments and the payment references; `rates.ts`: the exchange rates; `deposits.ts`: deposits, their receipts, flags and settings versions, and the USDT tables (S04: `usdt_deposits`, `usdt_transfers`, `usdt_scan_cursors`); `files.ts`: stored files; `auth.ts`: customer Better Auth tables; `admin.ts`: admin Better Auth tables, at most one admin row; `audit.ts`: the audit log; `notifications.ts`: the email outbox; `system.ts`: worker heartbeats), re-exported from `src/schema/index.ts`. Better Auth tables keep the property names Better Auth expects.
- `src/schema/columns.ts`: `id()`, `timestamps()`, `archivedAt()`, `amountUnits()`, `currencyEnum`. Enums reuse the `as const` lists of `@vertex-digital/contracts`.
- `src/audit/`: `recordAudit(tx, entry)`, the only way to write audit entries, inside the transaction of the change; details are checked against the action's shape in the contracts.
- `src/ledger/`: `postJournal` (the only way to write journals and postings) and `accountBalance`; `wallet.ts` (S02): `ensureCustomerWallet` and `ensureSystemAccount` (accounts created on first posting, inside its transaction), `findCustomerWallet`, `lockCustomerWallet` (the wallet created and locked, before a payment reference is claimed), `walletTimeline` and `walletBalanceAfter` (the timeline and its running balance, with each entry's adjustment or deposit), `customerWalletBalances`, `ledgerSummary`; `deposits.ts` (S03): `postDepositCredit` (an approved deposit's journal, `deposit:<id>`: two postings for USD received, four balanced per currency for SYP), and `postUsdtDepositCredit` (S04 M1: the network's `usdt_receipts` gives the exact amount received, the wallet gets whole cents, `deposit_rounding:USD` the rest); `usdt-deposits.ts` (S04): `creditUsdtDeposit`, the one credit of a USDT deposit (rule U7) shared by the worker's automatic credit and the admin's approval: deposit lock, wallet lock, TXID claim, journal, deposit and check updated, audit (the caller queues the email); `payment-references.ts` (S03): `claimPaymentReference` (the only writer of `payment_references`: one claim per method and trimmed, upper-cased reference, refused with `EXTERNAL_REFERENCE_TAKEN` and the holder in `details`) and `paymentReferenceOwner` (a USDT TXID is also looked up in the `0X` form S02 development rows may hold), `txidClaimed` (a SQL condition for lists outside the wallet module) and `txidHolders`. `src/orders/` (F11) will hold the order transition write path.
- `migrations/`: `0000_ledger.sql` and `0002_harsh_boom_boom.sql` (auth and staff tables, heartbeats) and `0003_broad_daimon_hellstrom.sql` (staff tables renamed to admin, ADR 0016) and `0004_s01_accounts.sql`, `0006_s02_wallet.sql`, `0008_s02_posting_position.sql` and `0009_wandering_captain_america.sql` (S03 rates and payment references) and `0011_polite_azazel.sql` (S03 deposits and files) are generated; `0001_ledger_guards.sql`, `0005_audit_guards.sql` (audit append-only, admin primary keys renamed) and `0007_s02_wallet_guards.sql` (adjustments append-only, the reversal check, a wallet's customer never changes) and `0010_s03_rates_guards.sql` (rates and payment references append-only, the claims of S02 manual deposits backfilled) and `0012_s03_deposits_guards.sql` (settings, receipts, flags and files append-only; `deposits_guard`: no delete, no change out of a final state or off the transition table, declared fields fixed, the quote changes only while pending and unfixed; the backfill again) and `0014_s04_usdt_guards.sql` (`decided_by` backfilled; `deposits_guard` again: `submitted → pending` only by a receipt request or a USDT TXID failure, a USDT deposit's dollars fixed, a decision without `decided_by` is the admin's; `usdt_deposits_guard`: no delete, the deposit's method and amount, what was shown and the bound transfer fixed, `deposit_open` mirrors the deposit and is kept by `deposits_sync_usdt_open`; transfers append-only) are hand-written; `0013_unknown_lionheart.sql` (S04 tables and columns) and `0015_thick_zzzax.sql` (the decision checks, after the backfill) and `0016_nappy_invisible_woman.sql`, `0017_ordinary_hawkeye.sql` (S04 PR 2: the USDT check errors `amount_too_small` and `txid_used`) are generated. `migrations/meta/` is drizzle-kit state: never read or edit it.
- `src/migrate.ts` (`runMigrations`) and `src/cli/migrate.ts`: the Drizzle migrations, then pg-boss's tables (`installPgBoss`), as the owner role under an advisory lock. `pnpm db:migrate`, deploys (`node packages/db/dist/cli/migrate.js`) and the tests' global setup all run it.
- `src/jobs.ts`: `PG_BOSS_SCHEMA` and `createPgBoss` (app role: no schema changes, no index rebuilds). The `pgboss` schema itself is created, owned by the owner role with default privileges for the app role, by `scripts/setup-local-db.mjs` and the production provisioning.
- `src/errors.ts`: `withoutQueryParameters(error)`: log and report a failed query by its cause, never with the parameters Drizzle puts in its message.
- `src/jobs.ts` also exports `transactionExecutor(tx)`: `boss.send(queue, data, { db: transactionExecutor(tx) })` sends a job in the caller's transaction.
- `src/testing.ts` (`@vertex-digital/db/testing`): test database URLs and the Vitest global setup the apps reuse.

## Roles (ADR 0014)
- The owner role (`DATABASE_OWNER_URL`) owns every table and runs the migrations (`pnpm db:migrate`, the migrate CLI, the tests' global setup). No app process uses it.
- The app role (`DATABASE_URL`) is what the API, the worker and the tests use. It owns nothing; default privileges give it `SELECT, INSERT, UPDATE, DELETE` on each new table, and append-only tables take the changes back.

## Rules the tests enforce
- `src/conventions.test.ts`: a business table is `{ id: id(), ...fields, ...timestamps(), archivedAt: archivedAt() }`; UUIDv7 `id` keys; every foreign key indexed; `timestamptz` only; no floating-point column; `*_units` columns are `bigint`; `idempotency_key` columns unique. An exception goes in `NOT_BUSINESS_RECORDS` or `NATURAL_KEYS`, with a reason; an append-only table also goes in `APPEND_ONLY_TABLES`.
- `src/ledger/guards.test.ts`: the app role is no superuser, owns no table and has no `UPDATE`, `DELETE` or `TRUNCATE` on journals and postings (no `DELETE`/`TRUNCATE` on accounts); it cannot disable the trigger or grant itself the privileges; the `append_only_guard` trigger refuses the owner role too; the app role cannot create temporary tables; journals have exactly their declared postings (none added later, a temporary table cannot fool the check) and balance per currency at commit; the database stamps `created_at`; a posting's currency is its account's; an account's id, code, kind, currency and customer never change; a customer is named on, and only on, a customer wallet.
- `src/audit/record-audit.test.ts`: an entry commits and rolls back with its change, wrong details are refused, the app role has SELECT and INSERT only, the trigger refuses even the owner, a second admin row is refused. `src/admin-rename.test.ts`: the rename keeps a Phase 0 staff row.
- `src/ledger/post-journal.test.ts`: balances, idempotency, refusals, and concurrency (parallel debits never overdraw, a key posted in parallel posts once, no deadlock).
- `src/ledger/payment-references.test.ts`: claims normalize and refuse a second claim naming the first, one of two parallel claims wins, the checks, the backfill, rates and claims append-only for the app role and the owner.
- `src/ledger/deposits.test.ts`: the deposit guard (transitions, final states, declared fields, quotes, receipt requests, no delete as the app role and the owner), the checks and the one-pending index, settings, receipts, flags and files append-only, the credit journals of M1 and M2 and their idempotency, deposits on the timeline, deposit claims of payment references; S04: system decisions and the decision checks, the guard's USDT bounce, `usdt_deposits` (insert checks, fixed fields, the bound transfer, the open-amount unique index and its mirror, no delete), `usdt_transfers` append-only, the settings defaults of older versions, the USDT credit journal, TXIDs claimed with `0x`.
- `src/ledger/wallet.test.ts`: adjustments are append-only for the app role and the owner, a reversal mirrors its original once and is never reversed, external references are unique per method in any case; wallets are created once under a race; the timeline's running balance across pages and equal times, and in write order when a debit's transaction began before the credit it spends; the summary splits real and test customers.
- `src/jobs.test.ts`: pg-boss is installed in a schema the app role does not own and cannot create tables in; the app role creates queues, sends and works jobs.

## The ledger (ADR 0003)
- Customer tables are referenced by append-only rows: a customer with a wallet can never be deleted (archive it). An admin is referenced without a foreign key (`audit_entries.actor_id`, `wallet_adjustments.admin_id`), so the single admin row stays replaceable.
- Write money only with `postJournal(tx, { idempotencyKey, kind, postings })`, inside the transaction that also writes the business change, its audit entry and its job. It is atomic on its own (a savepoint): a refusal leaves the caller's transaction usable.
- A journal declares its `posting_count`; the commit check refuses any other number of postings, so nothing can be added to a journal later. The database stamps `created_at`.
- A posting adds `amountUnits` to its account (negative takes from it); a balance is `accountBalance`, the sum. `position` (identity) is the write order, assigned after the wallet locks: timelines and running balances follow it, never the journal's `created_at` (its transaction's start). Customer wallets are USD, whole cents, never below zero; system accounts may go negative and keep sub-cent precision.
- `LedgerError` carries a contract code (`INSUFFICIENT_BALANCE`, `IDEMPOTENCY_KEY_REUSED`) for the API to return; any other `Error` is a bug.
- Transactions stay READ COMMITTED (PostgreSQL's default): `postJournal` refuses to debit a wallet under another isolation level.
- Corrections are new reversing journals. Never update or delete a ledger row, and never grant the app role privileges on it.
- A new append-only table (audit, order events) gets, in its custom migration, the `append_only_guard` trigger and the revokes of `0001_ledger_guards.sql` (from `PUBLIC` and every non-owner grantee, so the app role's name never appears in a migration); it joins `APPEND_ONLY_TABLES` and the trigger list in `guards.test.ts`.

## Rules to apply yourself
- A trigger function that reads a table names it with its schema (`public.<table>`) and has `SET search_path = public, pg_temp`, so no temporary table can stand in for it.
- Money columns: `amountUnits('<name>_units')` next to `currencyEnum('currency')`, or a currency-fixed name (`price_usd_units`). Exchange rates: `numeric`. Amounts are JS numbers checked as safe integers; math on them lives in `@vertex-digital/contracts`.
- Idempotency keys and external references (supplier attempt ids, Sham Cash transaction numbers, `(network, txid)`) get unique constraints.
- Migrations must stay backward compatible (expand, then contract); never edit one once generated; hand-written SQL goes in `drizzle-kit generate --custom`; never `drizzle-kit push`.

## Tests
Vitest's global setup migrates the test database as the owner (`TEST_DATABASE_OWNER_URL`); the tests run as the app role (`TEST_DATABASE_URL`), and as the owner only to prove a guard refuses it. Both roles come from `pnpm db:setup-local`; neither may be a superuser, or the privilege tests prove nothing. Ledger rows written by tests stay in the test database (append-only by design); every test uses new accounts and keys, so runs never collide.

Run: `pnpm --filter @vertex-digital/db test`. CI fails if `pnpm db:generate` produces a diff: commit the schema and its migration together.
