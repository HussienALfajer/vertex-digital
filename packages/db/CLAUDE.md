# packages/db

Drizzle schema, migrations, the database client and the shared money write paths (ADR 0002, 0003, 0011, 0014). Schema changes follow the `db-migration` skill.

## Layout
- `src/schema/<module>.ts`: tables of one owning API module (`wallet.ts`: the ledger, the wallet adjustments and the payment references; `rates.ts`: the exchange rates; `settings.ts`: the store switches (S05: `store_switch_changes`, append-only, `created_at` stamped at insert); `deposits.ts`: deposits, their receipts, flags and settings versions, and the USDT tables (S04: `usdt_deposits`, `usdt_transfers`, `usdt_scan_cursors`); `files.ts`: stored files; `auth.ts`: customer Better Auth tables (S22: `customer_passkeys`, credentials deleted on removal and reset, `credential_id` unique, migration `0093_narrow_living_tribunal.sql` generated with the `customer_passkey_added` template); `admin.ts`: admin Better Auth tables, at most one admin row; `audit.ts`: the audit log; `notifications.ts`: the email outbox, and (S05) `customer_notifications` (only `read_at` changes, once; never deleted) and `notification_preferences` (a missing row is on; S15: `push` beside `email`), and (S15) `push_subscriptions` (unique endpoint, deleted with its session by the foreign key; device state, never archived); `system.ts`: worker heartbeats; `telegram.ts` (S05 F07): `telegram_links` (one live link, a partial unique index), `telegram_link_codes`, `telegram_messages` (the bot's outbox), `telegram_updates`, `telegram_prompts` (one open question; a deposit question names its deposit and submission, a check), `telegram_deposit_cards` (one card per deposit submission), `telegram_bot_state` (one row)); `catalog.ts` (S06 F08): `catalog_categories`, `catalog_games`, `catalog_input_fields`, `catalog_products` (business tables: slugs and field keys unique across archived rows, names unique among unarchived siblings, partial unique indexes; checks for bounds, whole cents and code-only text); `quick-links.ts` (S22 DL2, DL4, owner `catalog`; apart because it references both `catalog_products` and `orders`): `quick_link_events` (opens and attributed orders, `order_id` unique, never changed, deleted after 90 days by `orders.sweep`; migration 0092's guard), and `catalog_products.quick_code` drawn by `catalog_quick_code()` (migration 0090) and never changed; `product-alerts.ts` (S22 F42, owner `catalog`): `product_alerts` (customer preference data: one active alert per customer, pack and kind, a partial unique index; checks tie the baseline to price drops and the end to the status; deleted 90 days after ending by `orders.sweep`); `support_tickets.order_problem` (S22 OP5: only on order tickets, fixed by migration 0095's guard); `price-lists.ts` (S20 F29, owner `pricing`; apart so `auth.ts` can reference it): `price_lists` (seeded roots, one live list per root kind, names unique among live lists, a parent for custom lists only); `pricing.ts` (S06 F10): `margin_rules` (S20: per list, `price_list_fixed_prices`, the price rows' list, source and fixed price) (one live rule per target, one live global rule, `target_id` null only for global, no foreign key: the target is the catalog's); S07: `product_prices` (append-only, whole cents above the cost, stamped with `clock_timestamp()`) and `price_reviews` (one open per product; `price_reviews_guard`: a decided review never changes, the product and the price held are fixed, no delete); `suppliers.ts` (S07 F09): `suppliers` (seeded; ADR 0031 left `wdgzone`, `manual`, `fake`; S19 added `fazercards`), `supplier_credentials`, `supplier_offers`, `supplier_cost_changes`, `supplier_sync_runs` (one running per supplier; `supplier_sync_runs_guard`: only a running run changes, no delete), `supplier_calls`, `supplier_health_changes`, `supplier_balance_reads`, `supplier_policy` (seeded), `product_routes` (an offer serves one live route; S17: a product may have several live routes of one supplier, `price_basis`, `expected_delivery_minutes` and `hard_limit_minutes` with their timing check), `supplier_webhook_events` (S08: one per supplier event id, only the processing columns change, once); append-only ones stamped with `clock_timestamp()`; `orders.ts` (S08 F11): `orders` (`orders_guard`: never deleted, a terminal order never changes, identity, price and fields fixed, transitions on ADR 0004's table, units never go back; checks tie the totals, quantities, refund and the status's times), `order_events`, `order_codes`, `order_code_reveals`, `order_policy` (append-only, seeded), `fulfilment_attempts` (`fulfilment_attempts_guard`: never deleted, a delivered or failed attempt never changes; a route once per order, one open attempt per order; S11: `kind` `routed` or `admin_fulfil`, the delivery proof used once); S09: the reservation and player-check columns of `orders` (`orders_guard` lets the price columns change only on `awaiting_balance → paid`; `orders_notify` sends `customer_orders` on every insert and status change) and `player_checks` (a cache: the app role selects, inserts and deletes, never updates); S10: `checkouts` (`checkouts_guard`: only `finished_at`, once; no delete), the checkout and gift columns of `orders` (fixed by `orders_guard`; `orders_checkout_guard`: a checkout order carries its checkout's journal and customer, a single order never takes a checkout's journal; the purchase journal is unique only among single orders), `saved_players` (the customer's own rows, deleted for real; one per `(customer, game, fields_hash)`) and `order_share_links` (`order_share_links_guard`: order, kind and token fixed, a revoked link never changes, no delete; ## Roles (ADR 0014)
- The owner role (`DATABASE_OWNER_URL`) owns every table and runs the migrations (`pnpm db:migrate`, the migrate CLI, the tests' global setup). No app process uses it.
- The app role (`DATABASE_URL`) is what the API, the worker and the tests use. It owns nothing; default privileges give it `SELECT, INSERT, UPDATE, DELETE` on each new table, and append-only tables take the changes back.

## The ledger (ADR 0003)
- Customer tables are referenced by append-only rows: a customer with a wallet can never be deleted (archive it). An admin is referenced without a foreign key (`audit_entries.actor_id`, `wallet_adjustments.admin_id`), so the single admin row stays replaceable.
- Write money only with `postJournal(tx, { idempotencyKey, kind, postings })`, inside the transaction that also writes the business change, its audit entry and its job. It is atomic on its own (a savepoint): a refusal leaves the caller's transaction usable.
- A journal declares its `posting_count`; the commit check refuses any other number of postings, so nothing can be added to a journal later. The database stamps `created_at`.
- A posting adds `amountUnits` to its account (negative takes from it); a balance is `accountBalance`, the sum. `position` (identity) is the write order, assigned after the wallet locks (`postJournal` locks every wallet a journal touches, credits too, audit A4): timelines and running balances follow it, never the journal's `created_at` (its transaction's start). Customer wallets are USD, whole cents, never below zero and never above `Number.MAX_SAFE_INTEGER` units (audit A3); system accounts may go negative and keep sub-cent precision.
- `LedgerError` carries a contract code (`INSUFFICIENT_BALANCE`, `IDEMPOTENCY_KEY_REUSED`) for the API to return; any other `Error` is a bug.
- Transactions stay READ COMMITTED (PostgreSQL's default): `postJournal` refuses to debit a wallet under another isolation level.
- Corrections are new reversing journals. Never update or delete a ledger row, and never grant the app role privileges on it.
- A new append-only table (audit, order events) gets, in its custom migration, the `append_only_guard` trigger and the revokes of `0001_ledger_guards.sql` (from `PUBLIC` and every non-owner grantee, so the app role's name never appears in a migration); it joins `APPEND_ONLY_TABLES` and the trigger list in `guards.test.ts`.

## Rules to apply yourself
- Independent reads through `readAll(db, [() => read, …])` (`src/client.ts`), never `Promise.all`, when `db` may be a transaction (`Executor`): it runs them in parallel through the pool and one after another in a transaction. A transaction holds one client, which runs one query at a time; `Promise.all` there queued them inside pg, which warns since pg 8.20 and refuses from pg 9 (the production worker's startup warning, 2026-10-14). Parallel work only through the pool. `src/no-concurrent-queries.setup.ts` (and the api's and worker's `test/no-concurrent-queries.ts`) fails a test file that sends a query under the condition pg warns on (checked on the client, since Node prints the warning once per process); `src/read-all.test.ts` tests the helper.
- Inside a transaction every read goes through it, never through the pool (`this.db`, or a service method that reads `this.db`): the transaction holds a connection, often with a row or advisory lock, while the pool read waits for another, and ten such requests take the whole pool (F3-4, 2026-10-15). A helper or service method a transaction calls takes the executor (`db: Executor = this.db`), and a decision that may run inside a caller's transaction opens its own with `db.transaction` (a savepoint there). The API's and the worker's pools take `APP_POOL_LIMITS` (`src/client.ts`, `src/client.test.ts`): a 10 s wait for a connection or a 15 s wait for a lock fails, so such a slip fails in seconds instead of stopping the process; CLIs and migrations keep no limit. `poolReadsInTransactions` (`src/testing.ts`) records every pool query or pool transaction while a transaction of the same async flow holds a connection of that pool; `src/no-pool-reads-in-transactions.setup.ts` and the api's and worker's `test/no-pool-reads-in-transactions.ts` fail a test file that triggers it.
- A trigger function that reads a table names it with its schema (`public.<table>`) and has `SET search_path = public, pg_temp`, so no temporary table can stand in for it.
- Money columns: `amountUnits('<name>_units')` next to `currencyEnum('currency')`, or a currency-fixed name (`price_usd_units`). Exchange rates: `numeric`. Amounts are JS numbers checked as safe integers; math on them lives in `@vertex-digital/contracts`.
- Idempotency keys and external references (supplier attempt ids, Sham Cash transaction numbers, `(network, txid)`) get unique constraints.
- Migrations must stay backward compatible (expand, then contract); never edit one once generated; hand-written SQL goes in `drizzle-kit generate --custom`; never `drizzle-kit push`.

## Tests
Vitest's global setup migrates the test database as the owner (`TEST_DATABASE_OWNER_URL`); the api and worker suites run on `TEST_WORKERS` databases of their own each (`<test database>_<suite>_<n>`; `pnpm db:setup-local` creates as many as this machine uses, and the suites' global setups create missing ones as the owner role, which may create databases locally and in CI only), so the three suites run at once; each suite holds an advisory lock for its run (`holdTestDatabases`), so a second run of it waits for the first; the tests run as the app role (`TEST_DATABASE_URL`), and as the owner only to prove a guard refuses it. Both roles come from `pnpm db:setup-local`; neither may be a superuser, or the privilege tests prove nothing. Ledger rows written by tests stay in the test database (append-only by design); every test uses new accounts and keys, so runs never collide.

Run: `pnpm verify packages/db/src/<file>.test.ts` (one file) · `pnpm --filter @vertex-digital/db test` (the suite). CI fails if `pnpm db:generate` produces a diff: commit the schema and its migration together.
